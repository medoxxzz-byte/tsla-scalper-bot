# قائمة نشر واعتماد المرحلة A — هوية الحدث

**الهدف:** تحويل طبقة V17/V18 من MVP Pilot إلى طبقة جمع رسمية منضبطة، من دون تغيير منطق الإشارات أو رسائل Telegram.

## ترتيب النشر

| الترتيب | الإجراء | معيار النجاح |
|---:|---|---|
| 1 | اعتماد ترحيل Neon | وجود حقول الهوية وجدول `webhook_receipts`، ووسم الـPilot فقط |
| 2 | تحديث النسخ الاحتياطي | تصدير `tm_research_events` و`webhook_receipts` والعروض اللازمة مع اختبار استعادة |
| 3 | نشر `event_store.py` وملفات الاختبار على Render | `storage_status` يعيد `ok` و`identity_version: event-v2` |
| 4 | اختبار Telegram الآمن | تخزين حدث اختبار ورقم receipt ناجحان بينما دالة Telegram محاكاة بالفشل محلياً؛ لا ترسل Telegram فعلياً |
| 5 | اختبار restart + replay | بعد إعادة تشغيل Render، إعادة حمولة اختبار مطابقة تنتج receipt `duplicate` لا حدثاً جديداً |
| 6 | تحديث Pine V17 وV18 | حفظ كل سكربت وإضافته إلى الرسم مع بقاء المنطق والمواعيد كما هي |
| 7 | تحديث Alerts | إعادة إنشاء/تحديث تنبيهَي webhook ليستخدما نسخة السكربت التي تستدعي `alert()` |
| 8 | تحقق Pine-equivalent | إرسال حمولة اصطناعية بالصيغة النهائية مباشرة إلى Render، ثم تحقق Neon من `new` |
| 9 | أول حدث طبيعي | أول حدث TradingView طبيعي بهوية `event-v2` يبدأ العينة الرسمية فقط |

## اختبارات القبول الملزمة

| الاختبار | الدليل المطلوب |
|---|---|
| حدث جديد صحيح | صف حدث رسمي + receipt `new` |
| إعادة مطابقة متتالية | receipt `duplicate` فقط |
| إرسالان متزامنان | حدث واحد وسجلّا استلام |
| تعارض CMF/MOM | الأصل ثابت وreceipt `conflict` يحفظ الحقول المتغيرة |
| هوية ناقصة | receipt `invalid` بلا حدث رسمي |
| restart ثم replay | receipt `duplicate` بعد تشغيل جديد |
| فشل Telegram | التخزين ينجح وفشل الإرسال لا يعطل الحفظ |
| النسخ الاحتياطي والاستعادة | يشمل الأحداث والإيصالات والعروض |

## إعلان البداية الرسمية

لا نعلن اكتمال الاعتماد إلا بعد نجاح هذه القائمة على بيئة الإنتاج. عندها فقط: **تبدأ العينة الرسمية من أول حدث طبيعي يحمل `schema_version: event-v2` و`data_quality_tier: official`.** جميع الصفوف السابقة تظل Pilot، بما فيها أي بيانات اختبار موسومة `test`.
